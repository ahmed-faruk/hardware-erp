# Database

Two databases hold the same model: **IndexedDB via Dexie** on every device (source of truth for selling) and
**Postgres on Supabase** (aggregates all devices, backups, manager reports). Server names are `snake_case`;
the same fields in Dexie and TypeScript are `camelCase` (`unit_cost` ↔ `unitCost`). Business rules that produce
these rows are in `.claude/skills/hardware-erp-domain`; sync rules in `.claude/skills/offline-sync-engine`.

## 1. Stack
| Layer | Tool | Notes |

## 3. Conventions
- Money: `bigint` piasters (125.50 EGP = 12550). Quantity: `bigint` milli-units (1.5 m = 1500). Percent: `int` basis points (12.5% = 1250).
- Time: `timestamptz` on the server, ISO 8601 strings locally. Business day = Africa/Cairo date.
- Ids: UUID v7 generated on the device. Legacy (OSPOS) rows: UUID v5 of `"ospos:<table>:<id>"`.
- Human numbers: `<devicePrefix>-<TYPE>-<seq6>` unique per company (e.g. `K1-INV-000245`).
- Enums are `text` with a `check` constraint (easier to evolve than Postgres enums).
- No hard deletes of synced data: master data gets `deleted_at`; documents get a reversing document.

### Common columns (every synced table)
| Column | Type | Rule |
| --- | --- | --- |
| `id` | uuid PK | set by the device |
| `company_id` | uuid not null | from the device, checked by RLS |
| `device_id` | uuid | device that created the row |
| `created_by` | uuid | worker id (null for system rows) |
| `created_at`, `updated_at` | timestamptz | `updated_at` set by trigger on the server |
| `version` | int default 1 | +1 on every master-data change |
| `deleted_at` | timestamptz null | soft delete (master data only) |
| `server_seq` | bigint | global sequence, set by trigger, used by pull |

| --- | --- | --- |

### 4.5b Sync support tables (server only, never synced)
| Table | Columns | Notes |
| --- | --- | --- |
| `device_activations` | device_id, code_hash (sha256), expires_at, used_at | one-time codes printed on the Mac (`npm run device:add`); RLS on, no client grants |

## 5. Relationships
- category 1—n products; product 1—n product_units, barcodes, stock_movements.
- customer 1—n sales_invoices, sales_returns, customer_receipts, party_ledger rows.
- supplier 1—n purchase_invoices, purchase_returns, supplier_payments, party_ledger rows.
- document 1—n lines; document 1—n payments (`document_type` + `document_id`); document 1—n ledger rows (`doc_type` + `doc_id`).
- sales_return_line n—1 sales_invoice_line (`original_line_id`); returned qty per original line = Σ return lines.
- shift 1—n cashier documents and cash_movements; device 1—n shifts; worker 1—n documents (`worker_id`).
Server enforces FKs; Dexie does not, so commands validate references before writing.

## 6. Indexes
- Server: unique `(company_id, number)` per document table; unique `(company_id, code)` on barcodes;
  `(company_id, server_seq)` on every synced table; `(product_id, warehouse_id)` on stock_movements;
  `(party_type, party_id)` on party_ledger; `(cash_account_id, occurred_at)` on cash_movements; `(issued_at)` on documents.
- Dexie: index only what is queried — e.g. `products: 'id, &sku, categoryId, *searchTokens, updatedAt'`,
  `stockMovements: 'id, [productId+warehouseId], docId, occurredAt'`, `salesInvoices: 'id, &number, customerId, shiftId, issuedAt'`.

## 7. Migrations
Server:
1. `supabase migration new <verb_object>` (e.g. `add_cash_transfers`).
2. Write SQL: table + common columns + trigger + RLS policies + grants in the SAME migration.
3. `supabase db reset` locally, then `supabase test db`.
4. Must be backward compatible with the deployed app (expand → deploy → contract). CI applies it to staging; merge applies it to production before the frontend deploys.
Local:
- New `db.version(n).stores(...)` block + `.upgrade()`; never edit an old version block; bump `SCHEMA_VERSION` used by backups.
Never change production by hand (SQL editor) to skip a migration.

## 8. Seed and test data
- `supabase/seed.sql`: one company, branch, main warehouse, cash accounts, expense categories, 3 workers with test PINs, 20 products.
- `tests/fixtures/generate.ts`: deterministic fake data (20,000 products, 500 customers, 50,000 sales) for performance tests.
- Real shop data never appears in seeds, fixtures, tests, screenshots, logs or commits.

## 9. Legacy import (OSPOS)
Source: `migration-data/ospos-export-YYYY-MM-DD.json` produced by `tools/ospos-export/export.js` (browser export;
the OSPOS backup button returns HTTP 500 and phpMyAdmin is not available). Mapping and validation: skill `ospos-migration`.
- Products, customers, suppliers, categories, workers (names only) → master tables with `legacy_*_id`.
- Sales, returns, receivings, expenses → documents with `is_legacy = true`, no ledger rows; lines keep `legacy_text` when
  the product cannot be matched by barcode/name.
- Openings at cutover: stock from OSPOS quantities; customer/supplier balances from the owner-approved sheet.

Import details (phase 4): legacy rows carry `is_legacy = true` on documents AND on their child tables (lines, payments), and
`pull_changes` never returns them. OSPOS cash rounding (paid 75.30 on a 75.25 sale) is kept in `sales_invoices.cash_rounding`.
Receivings with no known supplier link to the placeholder supplier "مورد غير محدد (أرشيف قديم)". `import_batch(table, rows)` is
service-role only and idempotent. Tool and steps: `tools/ospos-import/README.md`.

## 10. Size and retention
- Real volume: ~55 sales/day; legacy archive = 68,504 sales/returns with 324,602 lines + 5,343 receivings (23,740 lines). Estimated server size incl. legacy archive and indexes: 150–250 MB
  → fits the 500 MB free tier; measure monthly (`select pg_database_size(current_database())`), alert at 70%.
- Devices keep: master data fully; own documents ≥ 13 months; other devices' documents 13 months on PCs, 90 days on phones.
  Legacy archive stays on the server only (manager reports online).

## 11. Production safety
- Nightly encrypted `pg_dump` (GitHub Actions artifact, 30 days) + local device backups (`BAK-01`).
- Never run `supabase db reset` or destructive SQL against staging/production.
- Multi-row business writes happen in one transaction (Dexie transaction on device, one RPC call on server).
- Access rules: `docs/SECURITY.md`. RPC contracts: `docs/API.md`.
