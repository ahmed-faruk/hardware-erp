# قياس الأداء — الخط الأساسي (١٢ أكتوبر ٢٠٢٦)

الأدوات: `npm run perf:seed` (بيانات وهمية بحجم النظام القديم على الـ Mac)، `npm run perf:explain` (زمن كل تقرير على السيرفر)،
`npm run perf:screens` (Playwright: زمن كل شاشة وكل تبويب تقارير)، وقياس حي على staging من Chrome (قراءة فقط).

## ١) على الـ Mac (قاعدة محلية، ٦٥ ألف فاتورة و٣٢٠ ألف سطر)

| الشاشة                                                                    | الزمن                                    |
| ------------------------------------------------------------------------- | ---------------------------------------- |
| شاشات الأصناف/العملاء/الموردين/المشتريات/المصروفات/العمال/الإعدادات/البيع | 20–350 ms                                |
| التقارير (التبويب الافتراضي «نظرة ذكية»)                                  | **1,700 ms** (مهمتين طويلتين في المتصفح) |
| تبويب «نظرة ذكية» وحده                                                    | **1,100 ms**                             |
| مبيعات / ربح / مشتريات / مصروفات / تصنيفات (شهر)                          | 90–160 ms                                |
| تصنيفات ٤٠٠ يوم                                                           | 370 ms (السيرفر 250)                     |
| كاشير: دخول → شاشة البيع                                                  | 930 ms · دفع → تم 1,080 ms               |
| أول تفعيل لجهاز جديد (سحب البيانات)                                       | 12 ثانية                                 |

زمن السيرفر لكل تقرير (٤٠٠ يوم): مبيعات 70–90 ms، ربح 118 ms، تصنيفات 326 ms، حركة صنف (١٠ سنين) 78 ms.
الخطة بتقول إن الفلتر `(issued_at at time zone …)::date` بيمنع استخدام الفهرس: قياس مباشر لشهر واحد = **52 ms** بقراءة كل الجدول
مقابل **0.6 ms** بالفهرس (أسرع ~٨٠ مرة)، وجدول `sales_invoice_lines` ما فيهوش فهرس على الصنف (بحث حركة الصنف = قراءة ٣٢٠ ألف سطر، 90 ms).

| الطلب                                 | الزمن                                 |
| ------------------------------------- | ------------------------------------- |

## ٣) الخلاصة

- الشبكة وملفات الموقع مش هي المشكلة (٢٣٠ ms للصفحة، ١٠٠ ms لكل طلب).
- البطء بيحصل في **أول طلب بعد فترة** (ذاكرة قاعدة البيانات في الخطة المجانية بتبرد: 2.5 ثانية) وفي التقارير اللي بتقرأ جداول النظام القديم كلها.
- على الجهاز، «نظرة ذكية» (التبويب اللي بيفتح أول) هي أبطأ حاجة: 1.1–1.7 ثانية وبتجمّد الشاشة (مهام طويلة).
- الإصلاحات المخطط لها (الجزء ٢ و٣ و٤): فلاتر بالفهرس، فهارس ناقصة، جدول ملخص يومي، تحميل التبويب المفتوح بس، وتصغير جداول التاريخ القديم
  (بيقلل اللي لازم القاعدة تقراه وبيحافظ على الذاكرة الساخنة).

## ٥) بعد الجزء ٣ (الجهاز) — السبب الحقيقي للبطء

الـ CPU profile (`npm run perf:profile`) بيّن إن **١.٥ ثانية** كانت بتضيع في دالة واحدة: كل صف (فاتورة/حركة) كان بيبني `Intl.DateTimeFormat` جديد
(تكلفته أكبر بكتير من الفورمات نفسه). على جهاز المحل (Windows 7 / Firefox) أبطأ ٤–٥ مرات، وده «البطء الغريب جدًا».
اتصلّح في `cairoParts` (نظرة ذكية) و`cairoTime` (كل الجداول) وكشف الحساب ونافذة المرتجع وفحص الساعة: فورمات واحد بيتبني مرة.

| الشاشة (محلي)                                                                                                                 | قبل      | بعد        |
| ----------------------------------------------------------------------------------------------------------------------------- | -------- | ---------- |
| التقارير (افتراضي «نظرة ذكية»)                                                                                                | 1,688 ms | **436 ms** |
| تبويب نظرة ذكية                                                                                                               | 1,099 ms | **194 ms** |
| مهام طويلة في المتصفح                                                                                                         | 2        | **0**      |
| كمان: تبويب «المخزون» بيقرأ من الجهاز لما يتفتح بس، وآخر نتيجة لكل تبويب وفترة بتظهر فورًا لما ترجعله والجديدة بتحل محلها.    |
| حماية من الرجوع للبطء: اختبار وحدة (٢٠ ألف تاريخ < 1.5 ثانية) وميزانية في `npm run perf:screens` (أي شاشة > 1.5 ثانية بتفشل). |
